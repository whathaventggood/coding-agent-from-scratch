# Coding Agent 演示与量化记录

更新日期：2026-09-24。本文区分已经观察到的结果与尚待补跑的实验；它不是稳定成功率声明。

## 一分钟演示

项目提供三个安装后命令：`coding-agent` 执行任务，`coding-agent-benchmark` 在隔离的临时 Git 工作区运行固定任务集，`coding-agent-evaluate` 汇总运行报告。典型闭环是：读取/搜索工作区 → 模型选择受控工具 → 显式授权后修改文件 → 运行本地白名单测试 → CLI 独立复验 → 输出工具轨迹、文件变化和 JSON 报告。失败时可由调用者显式选择恢复任务开始时的 Git 可见普通文件状态；不把它描述成沙箱或任意文件的事务回滚。

离线演示先运行：

```bash
.venv/bin/python -m pytest -q
.venv/bin/coding-agent --help
.venv/bin/coding-agent-benchmark --help
.venv/bin/coding-agent-evaluate --help
```

真实模型演示需要调用者在自己的终端配置 `DEEPSEEK_API_KEY`。每次使用一个尚不存在的输出目录：

```bash
.venv/bin/coding-agent-benchmark benchmark_tasks.json \
  --output-dir /tmp/coding-agent-benchmark-001
```

该命令调用真实模型、可能产生费用；临时任务工作区在任务结束后清理，输出目录保留每个任务的 JSON 报告和 `summary.json`。不要把密钥、私人工作区内容或未经检查的原始报告提交到仓库。`summary.json` 是两项固定任务的汇总，不是独立盲测集。需要重复试验时使用新目录编号，保留失败运行，再用 `coding-agent-evaluate` 汇总全部逐任务 JSON；不要只挑成功样本。

## 已观察到的真实模型结果

2026-09-23，同一份两任务清单、同一 DeepSeek 模型、每任务最多 8 次模型请求，分别在工作流指导加入前后运行一次。历史执行记录保存在工作区根目录的《学习规划与进度.md》；原始逐任务 JSON 未纳入仓库，因此下表属于有文字交接、但无法从本仓库原始报告重新计算的历史结果。

| 条件 | 任务成功且独立复验通过 | 模型请求总数 | 工具错误 | 最大消息峰值（近似字符） |
| --- | ---: | ---: | ---: | ---: |
| 工作流指导前 | 1/2 | 13 | 2 | 3205 |
| 工作流指导 v1 | 2/2 | 13 | 1 | 4721 |

关键案例是 `create-text-normalizer`：首次耗尽 8 次请求仍未创建缺失模块；加入工作流指导后，第 5 次请求创建文件，第 6 次执行定向测试，第 7 次执行完整测试，第 8 次返回完成，随后 CLI 独立复验通过。工作流指导要求在测试/导入指出缺失源文件且允许编辑时考虑创建文件，并避免无新证据地重复失败读取。消息峰值同时升高，说明这不是无代价的改进。

这个前后对比只能说明两次具体执行的差别。每种条件仅有一次、每次只有两个固定任务；不能把 2/2 宣称为总体 100% 成功率，也不能从中推断改进具有统计显著性。模型输出非确定性，任务集规模、难度与真实仓库也有差距。

## 下一次量化更新的验收口径

建议在同一提交和同一任务清单上连续运行至少 5 次，每次使用独立的新输出目录，记录每次的全部成功与失败。报告应同时给出：提交号、任务清单是否改动、模型、每任务请求上限、运行次数、任务成功数、独立复验通过数、失败类型、工具错误数和请求数。逐任务 JSON 应作为原始证据保留在本地；如果需要公开，只公开已审查和脱敏的报告。不同版本对比时保持任务、预算、验证方案一致，并同时报告成本与失败样本。
